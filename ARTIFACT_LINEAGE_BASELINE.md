### Why the artifacts diverged

**Verified overwrite mechanism:** `train_encounter_nn.py:main` writes the same unversioned
model/preprocessor/channel files, OOF encounter/player files and neural player-feature path.
It does **not** rebuild `player_features_cs2cd.parquet`, refit XGBoost, or recalibrate it.
`aggregate_player_features.py:main` only merges whichever neural feature file exists when
that separate command is run. Its gate checks `max_demos`, not parent artifact hashes.
Both MLP and temporal-CNN options use the same artifact stem for the same training mode.

**Verified boundary of mismatch:** the old neural values agree between the March Parquet,
the March31 player table and the August CSV. The April temporal OOF values form a second,
internally consistent generation. `enn_score_mean` differs on all 6,973 joined table rows,
with max absolute difference **0.411060**. This is not a row-order mismatch or a new
implementation of the 12 aggregate formulas: reaggregation reproduces the current output.

**Not established:** whether the older generation used MLP versus a different CNN checkpoint,
another sequence length, different channel preprocessing/resampling, seeds or optimization.
There is no old checkpoint/preprocessor/fold-model/run manifest to isolate those causes.
It would be scientifically wrong to label the historical XGBoost inputs “generated by the
released CNN” solely because they use `enn_*` column names.

The April17 folder supplied by the owner, `C:/NullCS/.push-main/main`, is a Git worktree at
`d98adc4`. It contains curated source/site files, but no model weights, preprocessing pickles,
training tables or OOF files. Adjacent `docs/cnn_experiments.md` and `research_snapshot.md`
call the temporal CNN an experimental, non-champion branch. This corroborates the possibility
of a changed neural model, but does not identify the missing generator. Relevant available
Git history does not recover those private binary artifacts. `C:/NullCS` is a junction to
`C:/ClarityCS`, not another independent model backup.

**Verified CSV/Parquet mechanism:** `evaluate_xgb_gridcv.py:main` always writes OOF CSV,
but writes Parquet only when `--write-oof-parquet` is passed. `calibrate_model.py:load_oof`
prefers existing Parquet. Thus a newer evaluation CSV can coexist with an older calibration
input without any error. The observed dates/values fit that mechanism. Exact historical
command lines/library versions are not retained; changed folds/features can explain changed
predictions, but their individual contributions cannot be isolated without those old runs.

### Why this matters numerically

Read-only sensitivity test: keep the shipped XGBoost fixed; substitute only the current
12 neural aggregates into 6,886 historical player rows. Mean absolute raw-score change is
**0.029913**, maximum **0.823032**, and **125 rows cross 0.5**. This is a deliberately
constructed feature-substitution test, not new-match accuracy, not an ablation retraining,
and not the exact outputs of the complete current raw-demo pipeline. It demonstrates that
the lineage mismatch is large enough to matter to decisions.

One historical selective-activation value is **0.875** versus **0.660** in the current table
for the same player-match. The ordered 449-name hash is unchanged. A feature-name hash
protects order/names, not formula versions, reference populations or numerical values.

Separate discovered issue, **not changed**: `aggregate_encounter_scores` sorts scores but
indexes hard/low-visibility subsets using an unsorted NumPy boolean mask. In a three-row
diagnostic with scores `[0.1,0.9,0.2]` and only the first row marked hard, it returns hard
mean **0.9**, while the marked row is **0.1**. Kill-end uses aligned pandas indexing and
returns 0.1. Reproducibility of the current aggregates does not validate intended subset
semantics. Correcting this requires a versioned feature change and retraining, not a silent
edit to the released stack. It does not explain old/current aggregate-generation lineage.

Currently, aggregation computes four shrinkage medians over the input dataset before
cross-validation, while single-demo inference computes them over that match. This both
exposes validation covariates during research preprocessing and changes reference population
at inference. Do not confuse this unsupervised/transductive problem with supervised CNN
label leakage; both matter, but have different mechanisms.

## 4. Splitting and two different evaluation questions

### Track F: evaluate the exact shipped pipeline

Freeze all bytes, parser/runtime, feature/scoring semantics and thresholds first. Collect
new demos after the evaluation plan is frozen; exclude every known training, benchmark,
calibration and development match (including duplicate recordings). Use provenance and
real participant IDs to check overlap with known training players where possible.
Do not recalibrate, retune or change reference medians on this test set. Run the released
end-to-end pipeline and evaluate its actual review ranking, raw score, calibration, coverage
and failures. This is how to test the **shipped predictor** without refitting it.

You cannot retroactively make the released checkpoint held out by repartitioning the old
dataset: its weights already learned from those matches. Unknown anonymized player overlap
must be disclosed; new-source/date holdout helps but cannot prove player independence.

### Track R: reproducible corrected learning procedure

Use old research data for internal development; reserve a **separate new external test**
for the final chosen candidate. Historical hyperparameter selection has already consulted
the old data, so even a corrected mechanical CV cannot erase that adaptive history.

Before any split, create indivisible groups by unioning:
1. identical demo hashes and same-match/duplicate-recording fingerprints;
2. known sessions and all windows from a match;
3. matches sharing a verified real player ID, when claiming unseen-player generalization.

Never union `Player_1` across CS2CD matches: it is an anonymized slot, not a persistent
identity. Give that subset a **match-disjoint / player-overlap-unknown** designation.
Do not split a match by eligible attackers; excluded players and victims still affect overlap.

Observed provisional graph from encounter attacker/victim IDs: pro matches form components
of **95, 4 and 1 matches**. A complete participant registry may only merge these further.
Therefore balanced pro representation in every player-disjoint fold is impossible with the
current cohort. Keep the 95-match component intact; report the resulting source imbalance
and a dedicated pro-held-out stress result. Do not split it for nicer-looking metrics.

Proposed internal outer scheme: **5 group-disjoint folds**, balancing match-label burden
and source/map as far as indivisible groups permit. Assign groups before filtering eligibility.
For each outer fold: 20% target held-out evaluation groups, 80% outer training groups.
Within that outer training set, reserve approximately **20% for calibration** (about 16%
of all groups), leaving approximately **64% for stack development**. Percentages are targets,
not exact promises; component sizes and both-class requirements take precedence.
Store exact assignments/class/source/coverage counts before scoring. If a feasible
calibration slice is too small or single-class, redesign the split before fitting rather
than borrowing outer-test labels. No actual assignment is approved/frozen yet.

## 5. Leak-free training inside each outer fold

For a first corrected baseline, freeze hyperparameters and feature policy in advance;
do not launch a broad model search. Let D = development, C = calibration, T = outer test.

1. Partition D into four grouped stacking folds H1..H4.
2. For each Hj, fit the CNN **only within D minus Hj**, with its own internal grouped
   early-stopping subset drawn from D minus Hj. Fit imputation/scaling only on the actual
   CNN fitting subset. Neither early stopping nor preprocessing may use Hj, C or T.
3. Predict Hj encounters and aggregate them by player-match. Each D meta-training row
   now has CNN features generated without its held-out group, and without C/T labels.
   Persist the producing checkpoint, preprocessing and exclusion-group identifiers per row.
4. Fit XGBoost on D's handcrafted features plus these OOF neural features. Compute class
   weights from D only. Fit population references on D and serialize them; never mix C/T
   into global medians. Match-local descriptive statistics are allowed if the same full-match
   information is available in retrospective deployment and used identically at inference.
5. Fit the deployment CNN on all D with epochs fixed from the inner early-stopping results,
   and fit its preprocessor on D. Predict C and T with this CNN and the D-trained XGBoost.
   The full-D versus inner-fold CNN distribution difference is ordinary stacking shift:
   quantify it and validate on C/T; it is not permission to reuse held-out labels.
6. Fit a predeclared calibrator on C scores/labels only. C cannot tune CNN/XGBoost or be
   reported as test performance. Keep original calibration semantics in Track F; the
   corrected calibrator is a separate, versioned artifact.
7. Score T once through the whole chain. Apply the predeclared evidence downweight and
   actual review ordering. Report raw/calibrated/review results separately; measure ties.

If tuning XGBoost or CNN hyperparameters later, validation must rerun this **whole fitting
recipe** within the training portion of each tuning split. Tuning XGBoost directly on one
globally precomputed CNN OOF table is not enough. Nested selection may add many fits;
it is not included in the first fixed-configuration baseline's cost below.

**Is OOF mandatory?** Not if CNN training, XGBoost training and calibration use entirely
disjoint datasets. That simpler holdout-stacking design is valid but data-inefficient.
For reusing development matches at both learned stages as NullCS does, grouped CNN
cross-fitting inside the outer partition is the practical recommendation.
See [scikit-learn's stacking explanation](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.StackingClassifier.html)
and [nested model-selection example](https://scikit-learn.org/stable/auto_examples/model_selection/plot_nested_cross_validation_iris.html).

### Concrete leakage example

Suppose Mirage match M is held out from XGBoost. Train player row P's CNN features using
a CNN trained on all matches except P's fold. If M belongs to that CNN's training set,
M's labels influenced P's neural features. XGBoost sees those features even though M's own
row was excluded. M's own grouped OOF generator excludes M, but can include other matches
in the outer held-out set T. Even aligning the original fold assignments does not remove
the indirect path through CNN features of the XGBoost training rows. “OOF” is relative to a particular training split,
not a universal property that makes a feature safe in every subsequent split.

In the corrected recipe, **every CNN used anywhere to construct D features excludes T**.
This closes the indirect path as well as the obvious direct one. Overlapping encounter
windows stay together because their entire match/component stays together.

## 6. Clean encounter experiment matrix

First establish the corrected baseline. The proposed factorial below changes the CNN's
context only; keep the handcrafted player-feature windows/formulas fixed for this study.
Recompute OOF CNN outputs, XGBoost and calibration for each configuration. Changing both
handcrafted context and CNN context would be a separate experiment.

Define a = fixed damage/kill anchor; P = pre-anchor tick extent; Q = post-anchor tick extent;
D=P+Q = elapsed tick span. Use **inclusive `[a-P,a+Q]`**, with at most D+1 original positions.
Observation count N is a separate resampling dimension, not original tick count.

| Span D | Post Q | Pre P | Maximum tick positions | CNN observations N |
|---:|---:|---:|---:|---|
| 96 | 0 | 96 | 97 | 32, 64, 96 |
| 96 | 16 | 80 | 97 | 32, 64, 96 |
| 96 | 32 | **64** | **97** | **32, 64, 96** — requested context |
| 96 | 48 | 48 | 97 | 32, 64, 96 |
| 144 | 0 | 144 | 145 | 32, 64, 96 |
| 144 | 16 | **128** | **145** | **32**, 64, 96 — existing context |
| 144 | 32 | 112 | 145 | 32, 64, 96 |
| 144 | 48 | 96 | 145 | 32, 64, 96 |

This is **2 durations x 4 absolute post allocations x 3 observation counts = 24 cells**.
Hold Q/N fixed to test duration; hold D/N fixed to test allocation; hold D/Q fixed to test
observation count. It is an absolute-post-allocation factorial, not a fixed-ratio factorial.
For a fixed 2:1 ratio comparison, 64/32 versus 96/48 is an additional planned contrast.
Machine-readable cells are in `research/encounter_context_matrix.csv`; none are approved to run.

Add a frozen released comparator R0. A retrained reference R1 uses the exact current
128/16 candidate selection, deduplication and 32-observation construction. Preserve candidate
filtering and index interpolation in the first matrix; separately study masks/time-grid/LOS.
Fix missing-event sentinel at the legacy **256 ticks** across N, avoiding today's `N*8`
semantic confound. N32 R1 must reproduce the baseline raw tensor before any model fitting.

Current stored windows do not retain an unambiguous originating damage/kill anchor. Before
the matrix, rebuild an anchor registry from events: stable match/round/attacker/victim/anchor
tick/type, with a map from each baseline deduplicated window to its originating anchors.
Choose a deterministic representative and preserve baseline encounter weighting across
cells; do not independently reselect convenient windows in each cell. Record exclusions
and common-support versus all-eligible results. Round/death/recording boundaries, sparse
candidate rows and missingness must be measured rather than silently filled as real evidence.

Q=0 includes the anchor and retains retrospective event-derived channels; call it an
**anchor-inclusive no-post control**, not a causal detector. A separate strict pre-event
control uses `[a-96,a-1]` and removes future/outcome information consistently from CNN and
handcrafted features. Damage-based anchor selection still conditions on a future event;
that control alone does not establish real-time deployment performance.

## 7. Compute, reproducibility and acceptance

**25 CNN fits + 5 XGBoost fits + 5 calibrator fits per configuration**. Early stopping uses
an internal subset without a second refit for each inner fold. If that refit is added, count
it explicitly. Three repeat seeds multiply these counts by three.
The complete 24-cell matrix would require **600 CNN + 120 XGBoost + 120 calibrator fits**
for one seed, before tuning or causal controls. It is **not** the recommended first launch.
First approve one corrected R1 configuration; next compare 128/16/N32 with 64/32/N32;
then vary N within those contexts before expanding the full matrix.

Existing observations: RTX5060Ti 16GB present; both available Torch environments CPU-only;

### Implemented protocol and intentional changes

- Five outer component folds; each has 572 development matches, 143-144 calibration
  matches, and 178-179 test matches. Components are formed before eligibility filtering.
  Four CNN cross-fit partitions produce development features; a fifth CNN fits all
  development data and predicts calibration/test data. XGBoost fits development only;
  isotonic calibration fits calibration only. Every preprocessor and class weight uses
  its fitting partition. Test groups reach none of these fits.
- **Predeclared deviation from section 5:** four CNN epochs were fixed from the released
  manifest before inspecting any new scores. No early-stopping selection was performed
  in this run. Architecture, 35 channels, 32 observations, batch 2,048, AdamW lr .001,
  weight decay .0001 and dropout .15 retained. XGBoost parameters were fixed to the
  historical selected configuration, with class weight recomputed inside each fit.
- Corrected `aligned-v2` encounter aggregation associates hard/low-visibility masks
  with their original rows. Existing weights continue to use `legacy-v1` by default.
- Corrected shrinkage fits its four references using development matches and persists
  them for inference. The 449 names/order remain fixed, but semantics are explicitly
  versioned; a name hash alone cannot authorize substitution of old/new models.
- No changes to parser, labels, encounter context, temporal resampling, CNN architecture,
  thresholds or review-score downweight formula. Historical artifact generation remains
  unresolved; the new run does not retroactively authenticate the old table.

`prepare_corrected_baseline.py` hashes original files and writes an immutable input
snapshot. The 894 demos form 797 known-identity/duplicate components; the largest is
95 professional matches. All 281,792 temporal windows remain with their match. Three
reconstructions (negative source 0, positive source 0, Pro001; 28/175/118 windows)
matched the raw cache within 1e-6, including missingness. This is a sampled cache check,
not proof that every historical source was generated by the same code.

`train_corrected_baseline.py` writes separate per-fold checkpoints, preprocessing,
fit/predict demo lists, per-row producing-checkpoint hashes, calibration predictions,
test predictions, model parameters, code hashes and timings. It refuses silent GPU
fallback, changed inputs, missing CNN player predictions and incomplete feature schemas.
The snapshot uses read-only memory-mapped temporal tensors; prediction transforms are
bounded to 4,096 windows. A failure records an explicit failed run once fitting begins.
